# Гибридная загрузка иконок: CDN vs локально

## Правило

- **Материалы** (`src/data/materials/`) — ВСЕГДА локально, из `public/assets/...`.
  Они участвуют в OCR-сравнении (`digit-matching.ts`/`template-matching.ts`
  матчат иконку в скриншоте инвентаря против байтов ЭТОГО файла) — CDN
  здесь в принципе не подходит.
- **Всё остальное** (аватары персонажей, созвездия, таланты, существа, рыбы,
  артефакты) — с CDN Enka Network: `https://enka.network/ui/{IconName}.png`.
  Используется только для отображения, в OCR не участвует.

Резолвер — `src/core/utils/cdnIcon.js` (`resolveIconUrl`).

## Почему не переключено сразу везде

Enka-имя иконки (`UI_AvatarIcon_Ayato` и т.п.) — это НЕ то же самое, что
`enkaId` (числовой id персонажа, `10000066`), уже присутствующий в данных
проекта. Соответствие числовой id → строковое имя иконки нужно взять из
каталога Enka (`enka.network`) — а `enka.network` недоступен из песочницы,
в которой это писалось (сетевой allowlist ограничен пакетными реестрами).
Поэтому:

1. Резолвер поддерживает graceful fallback: если для конкретного id нет
   записи в `*.generated.json` — используется прежний локальный путь
   (`item.avatar`/`item.icon` и т.д.), приложение не ломается.
2. `*.generated.json` в этой папке — заглушки (`{}`), закоммичены только
   чтобы резолвер и импорты не падали.
3. Реальные данные получаются через `scripts/fetch-enka-icon-map.js` —
   запусти его на машине С доступом в интернет (см. инструкцию в шапке
   самого скрипта, там же — что именно нужно проверить/поправить перед
   запуском, поскольку сам URL каталога Enka я тоже не смог проверить вживую).
4. После генерации файлов иконки соответствующих персонажей/оружия/
   артефактов подтянутся с CDN САМИ — без дополнительных правок в
   компонентах.

## Формат generated-файлов

Простой плоский `{ id: enkaIconName }`:

```json
{
  "ayato": "UI_AvatarIcon_Ayato",
  "diluc": "UI_AvatarIcon_Diluc"
}
```

Для составных сущностей (созвездия/таланты — по одному на персонажа И
слот) — составной ключ `"характерId:тип:слот"`:

```json
{
  "ayato:const:1": "UI_Talent_S_Ayato_01",
  "ayato:talent:attack": "UI_TalentIcon_Ayato_Attack"
}
```

## Уже реализовано (проверенный паттерн)

`src/features/profile/enka/EnkaBuildDetail.jsx` уже использует
`https://enka.network/ui/${artifact.icon}.png` — но там `artifact.icon`
приходит прямо в ответе Enka API на конкретный профиль (импорт чужого
профиля всегда возвращает актуальные имена). Для статических данных
проекта (страницы персонажей/оружия вне контекста профиля) такой строки
взять неоткуда — отсюда и генератор-скрипт выше.

## Что уже подключено к резолверу

- Аватар персонажа (`CharacterHeader.jsx`, `SaveCard.jsx`,
  `CalculatorSaveCard.jsx`, `ProfilePage.jsx`) — как образец паттерна.

## Что осталось подключить по тому же паттерну

Созвездия/таланты (`CharacterInfoPageView.jsx`, `MaterialsSetupModal.jsx`,
`TalentSection.jsx`), существа/рыбы (`CreatureModal.jsx`, `FishModal.jsx`),
иконки оружия (`WeaponHeader.jsx`, `WeaponSelector*.jsx`) — тот же вызов
`resolveIconUrl(...)` вместо прямого `/${item.icon}`, после того как для
них появится соответствующий `*.generated.json`.
